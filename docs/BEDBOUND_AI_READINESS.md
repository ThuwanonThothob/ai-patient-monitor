# ความพร้อมของ AI สำหรับผู้ป่วยติดเตียงและผู้สูงอายุ

เอกสารนี้อธิบายสถานะตามโค้ดและหลักฐานที่มีจริง ไม่ใช่การรับรองอุปกรณ์การแพทย์

## สิ่งที่ระบบทำได้แล้ว

- รับ HR, SpO₂ และ RR ต่อเนื่อง ตรวจคุณภาพ/ความใหม่ก่อนใช้
- แสดงค่าปัจจุบันและย้อนหลัง 1 ชั่วโมง, 6 ชั่วโมง, 24 ชั่วโมง และ 7 วัน
- ใช้โมเดล BIDMC สำหรับ forecast ระยะสั้นและ Isolation Forest สำหรับรูปแบบต่างจากชุดฝึก
- AI Agent เสนอรายการให้คนตรวจ รวมเหตุการณ์ซ้ำ และเก็บ audit trail
- มีแผนดูแล งานตามเวลา การรับผิดชอบ การตอบผู้ป่วย และ Web Push แบบเลือกเปิด
- มี runtime รับ pressure map 32×64, ตรวจ checksum โมเดล PMD, แสดงผล/งดสรุป และเก็บ Ground Truth แยกจากผล AI
- มี device-health registry, heartbeat watchdog และ alert สำหรับแบตเตอรี่ สัญญาณ เซนเซอร์หลุด และ calibration

## ช่องว่างสำคัญก่อนทดลองกับผู้ป่วยจริง

1. **อุปกรณ์จริง** — software contract และ simulated failure tests มีแล้ว แต่ยังต้องต่อ bench hardware
   3–5 ชุด ตรวจ timestamp/clock, reconnect, calibration และ sensor-off-body กับอุปกรณ์แต่ละรุ่น
2. **ข้อมูลกลุ่มเป้าหมาย** — BIDMC และ PMD ไม่ใช่ cohort ผู้สูงอายุ/ผู้ป่วยติดเตียงที่บ้าน
   ต้องมีโครงการเก็บข้อมูลพร้อม consent, ground truth จากบุคลากร และแยกผู้ป่วยระหว่าง train/test
3. **ความเสี่ยงเฉพาะผู้ป่วยติดเตียง** — แรงกด/การเปลี่ยนท่า, แผลกดทับ, การตกเตียง,
   ไข้, ความดัน, โภชนาการ/น้ำ, ขับถ่าย และการรับยา ยังไม่มี live sensors หรือ validated labels
4. **เกณฑ์เฉพาะราย** — โปรไฟล์มีช่วงอ้างอิงที่คนยืนยันได้ แต่ alert หลักยังต้องผ่านการออกแบบ
   และทบทวนโดยทีมคลินิกก่อนนำช่วงเฉพาะรายไปเปลี่ยนการแจ้งเตือนจริง
5. **การส่งต่อจริง** — คำขอติดต่อแพทย์/รถพยาบาลยังเป็นบันทึกในระบบ ต้องมี on-call roster,
   acknowledgement, SLA, escalation fallback และการทดสอบเมื่ออินเทอร์เน็ต/ไฟฟ้าขัดข้อง
6. **สิทธิ์และความเป็นส่วนตัว** — มุมมองแพทย์/พยาบาลปัจจุบันเป็นการจัดหน้าจอ ไม่ใช่ RBAC
   ต้องแยกสิทธิ์แพทย์ พยาบาล ญาติ ผู้ดูแลระบบ พร้อม consent, retention และ access audit
7. **การพิสูจน์ประสิทธิผล** — ต้องรายงาน sensitivity, specificity, false alerts ต่อ patient-day,
   missed-event review, calibration, subgroup performance และ drift จาก prospective pilot

## ลำดับพัฒนาที่แนะนำ

### ระยะ 1 — ความน่าเชื่อถือของข้อมูล

- ต่ออุปกรณ์จริง 3–5 ชุดใน bench test
- ต่อ device adapter จริงกับ MQTT contract และผ่าน simulated/bench failure tests ที่มีแล้ว
- กำหนดนิยามเหตุการณ์และวิธีบันทึก ground truth ร่วมกับแพทย์/พยาบาล

### ระยะ 2 — Controlled pilot

- ทดลองแบบ shadow mode: AI เสนอแต่ไม่ส่งผลต่อการรักษา
- วัด false alert, missed event, เวลารับทราบ และความครบถ้วนของข้อมูล
- ทบทวนเหตุการณ์ผิดพลาดทุกเคสและ freeze model/version ต่อรอบทดลอง

### ระยะ 3 — Workflow validation

- เพิ่ม RBAC, on-call routing, SLA และ fallback
- ทดสอบ backup/restore, ไฟดับ, เน็ตหลุด, sensor หลุด และ notification ไม่ถึง
- ให้คณะกรรมการจริยธรรม/ความเป็นส่วนตัวและทีมคลินิกอนุมัติก่อนขยายผล

เป้าหมายที่เหมาะสมในระยะนี้คือ **AI decision support ที่ตรวจสอบย้อนหลังได้** ไม่ใช่ AI ที่วินิจฉัย
สั่งรักษา หรือเรียกรถพยาบาลโดยไม่มีมนุษย์รับผิดชอบ
