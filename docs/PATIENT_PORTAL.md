# ฝั่งผู้ป่วย: ดูข้อมูลของตัวเองเป็นหมวด

หน้า `http://localhost:3001` เป็นพื้นที่ติดตามข้อมูลแบบอ่านอย่างเดียวสำหรับ
**ผู้ป่วยสาธิต** ล็อกอินด้วย A001–A020, B001–B020 หรือ C001–C020
ยังไม่เหมาะกับเวชระเบียนจริง: การรู้ ID ไม่ใช่การยืนยันตัวตน และยังไม่มีบัญชีญาติที่ได้รับสิทธิ์แยก

บัญชีสำหรับสาธิตการโต้ตอบโดยเฉพาะคือ `test_p` / `admin4321`
(ธุวานนธ์ ตอบโต้) และฝั่งแพทย์ `test_d` / `admin1234`
(ธุวานนธ์ โต้ตอบ) บัญชีผู้ป่วย TEST แยกจากทะเบียน 60 เตียง จึงไม่มีการสร้าง
ค่าสัญญาณชีพปลอมขึ้นมาให้ดูเหมือนเป็นค่าจริง

## หมวดที่ใช้งานได้

1. **ภาพรวม** — HR, SpO2, RR ล่าสุด สถานะข้อมูล ผล AI แบบภาษาง่าย
   งานเปิด/งานเสร็จวันนี้ และทางลัดไปหมวดอื่น เปิดรายละเอียดดู forecast เดิมได้
2. **แนวโน้มย้อนหลัง** — เลือก 1, 6, 24 ชั่วโมงหรือ 7 วัน สลับตัวแปรได้
   แยกแหล่ง BIDMC replay/MQTT/ไม่ทราบแหล่ง พร้อมสถิติ กราฟและตารางอ่านแทนกราฟ
3. **แผนดูแลของฉัน** — แผนที่บุคลากรยืนยันแล้ว งานรอรับ/รับแล้ว
   และรายการปิดวันนี้ ไม่มีปุ่มแก้แผน รับงาน หรือบันทึกผลแทนเจ้าหน้าที่
4. **แชททีมดูแล** — สนทนาสองทาง แสดงชื่อผู้ส่ง เวลา และสถานะอ่าน
   ข้อความผูกกับ session ไม่รับ Patient ID จากผู้ป่วย และไม่ส่งเข้า Gemini/ชุดฝึกโมเดล
5. **สรุปประจำวัน** — เลือกวันไทย อ่านสรุปจากข้อมูลที่มีจริง
   พร้อมดาวน์โหลด Text เฉพาะของตัวเอง ไม่ใช่รายงานภายในฉบับเต็มของบุคลากร
6. **ข้อมูลของฉัน** — โรค/ภาวะ ยาที่มีบันทึก ประวัติแพ้ และข้อจำกัด
   จากโปรไฟล์ฉบับที่ยืนยันแล้ว แยกออกจากชื่อ/อายุ/โรคในทะเบียนสังเคราะห์

## เตรียมข้อมูลให้ผู้ป่วยเห็น

ในเว็บบุคลากร `http://localhost:3000` เข้า **แผนดูแล** แล้วเลือก ID เดียวกัน:

- ข้อมูลการดูแล: บันทึกร่าง → ตรวจยืนยัน ผู้ป่วยจึงเห็นสี่ช่องที่กล่าวข้างต้น
  ฉบับร่างใหม่ไม่แทนฉบับที่ใช้อยู่ พักโปรไฟล์แล้วจะไม่แสดงข้อมูลฉบับนั้นในหน้าปัจจุบัน
- งานดูแล: สร้างร่างแผน → ตรวจยืนยันและเปิดใช้ ผู้ป่วยจะเห็นชื่องาน
  รายละเอียดแผน เวลาที่กำหนด และสถานะ จึงควรเขียนรายละเอียดส่วนนี้ให้ผู้ป่วยอ่านเข้าใจ
- บุคลากรรับงาน/ปิดงานตาม workflow เดิม ฝั่งผู้ป่วยโหลดสถานะใหม่ทุก 15 วินาที

ไม่เปิดเผย `care_notes` ในโปรไฟล์ บันทึกผล/เหตุผลข้ามงาน บันทึกตรวจทานรายงาน
audit log ชื่อบัญชีผู้ปฏิบัติ ผู้รับผิดชอบภายใน และข้อความเหตุผล alert ให้ patient API
ผ่าน response ที่เลือกส่งเฉพาะฟิลด์ ไม่ใช่เพียงซ่อนบนหน้าจอ
รายการยาที่บันทึกไม่ใช่ใบสั่งยาหรือคำแนะนำให้ปรับยาเอง

## เวลาและแหล่งข้อมูล

- ค่าปัจจุบันโหลดประมาณทุก 3 วินาที ซ่อนเมื่อเก่ากว่า 15 วินาที
  ผล ML ต้องใหม่พอด้วย และถ้าไม่มีข้อมูลจะไม่แสดงว่า “ปลอดภัย”
- ไม่เรียก `get_patient_details`/โมเดลประเมินอื่นซ้ำทุกครั้งที่ผู้ป่วยเปิดดู
  อ่านผลที่ worker ของ staff backend คำนวณไว้แล้ว ไม่มี worker ML ตัวที่สอง
- กราฟย้อนหลังใช้ค่าเฉลี่ยช่วง 1 นาที/5 นาที/15 นาที/1 ชั่วโมง ตามช่วงเวลาที่เลือก
  จุดว่างไม่ถูกเติมศูนย์ ค่าเฉลี่ยอาจซ่อนช่องว่างสั้นกว่าขนาดช่วง จึงแสดงสถิติความครอบคลุมประกอบ
- สรุปรายวันอ่านร่างที่ระบบเตรียมไว้ (โดยปกติทุก 5 นาทีขณะ staff backend ทำงาน)
  ถ้ายังไม่มีร่างจะสร้างสถิติของ ID นั้นตามคำขอ ปุ่มโหลดไม่ได้สั่ง AI เทรนหรือวินิจฉัยใหม่
- วันรายงานเป็น Asia/Bangkok; ข้อมูลอนาคตถูกตัดออก และรายงานวันนี้อาจยังไม่ครบวัน
- Text ผูกกับฉบับที่เปิดอ่าน หากร่างเปลี่ยนก่อนดาวน์โหลด API ตอบ 409
  ให้โหลดสรุปล่าสุดก่อน เพื่อไม่สลับเนื้อหารายงานโดยเงียบ ๆ
- ความครอบคลุมประมาณจาก snapshot ไม่ใช่ uptime อุปกรณ์ และไม่ใช่ความแม่นยำ AI
- ถ้าเพิ่งเปิดระบบ จะมีข้อมูลย้อนหลังเฉพาะที่บันทึกไว้ ไม่สร้างประวัติ 7 วันขึ้นมาให้

## API และการแยกสิทธิ์

ทุกเส้นทางใช้ ID จาก patient session บนเซิร์ฟเวอร์:

- `GET /api/me` และ `GET /api/me/report`
- `GET /api/me/trends?hours=1|6|24|168`
- `GET /api/me/care`
- `GET /api/me/daily?day=YYYY-MM-DD`
- `GET /api/me/daily/report?day=YYYY-MM-DD&digest=...`
- `GET /api/me/chat` และ `POST /api/me/chat`
- `WS /ws/me` ยังคงรองรับผลอ่านเฉพาะ ID ของเซสชัน

ไม่มี route ที่รับ Patient ID อิสระเพื่ออ่านคนอื่น ไม่มี route เขียนแผนหรือสั่งรักษา
cookie บุคลากรใช้เข้า patient API ไม่ได้ และ patient cookie ใช้เข้า staff API ไม่ได้
การเพิ่ม `patient_id=B001` ใน URL หลังล็อกอิน A001 จะไม่เปลี่ยนข้อมูลเป็น B001
ไม่ได้เปิดรายงาน raw หรือ staff route เดิมให้ผู้ป่วย

## รันและตรวจสอบ

จากรากโปรเจ็กต์:

```bash
.venv/bin/python scripts/run_ward.py
```

ถ้าระบบ launcher เดิมยังเปิดอยู่ ใช้ `--restart` เพื่อโหลด backend รุ่นใหม่
ไม่ต้องลบ DB หรือเพิ่ม dependency; สำหรับการรันแบบ production ต้อง build ทั้งสองพอร์ต
ตามคำสั่งใน README หลังแก้ frontend

การตรวจรอบนี้ใช้ฐานข้อมูล QA แยก ไม่อ่านหรือส่งข้อมูลผู้ป่วยจริง ไม่เปิด Gemini/Push
มีการทดสอบ ID isolation, ขอบเขตเวลา, ค่าว่าง/ซ้ำ, ฉบับร่าง, field allowlist,
ไฟล์ดาวน์โหลด และประวัติเก่า ตลอดจน build staff/patient และหน้าจอมือถือ

ยังต้องเพิ่ม verified login/สิทธิ์ญาติจริง และทดสอบการใช้งานทางคลินิกก่อนนำไปดูแลคนจริง
หน้านี้ไม่ใช่ช่องทางฉุกเฉินและไม่มีการติดต่อบุคคลหรือเรียกรถพยาบาลอัตโนมัติ
