# โปรไฟล์เฉพาะรายและสรุปการดูแลประจำวัน

ฟีเจอร์นี้ใช้กับทะเบียน **สาธิต 60 เตียง** เท่านั้น เป็นส่วนจัดบริบทและส่งต่อ
หลักฐานให้คนตรวจ ไม่ใช่โมเดลวินิจฉัยโรค ไม่เปลี่ยนแผนรักษา และไม่ใช่ระบบฉุกเฉิน

## เข้าใช้งาน

รันระบบตาม README แล้วเข้าเว็บบุคลากรที่ `http://localhost:3000`
เลือก **แผนดูแล → Patient ID** จะมีสามหมวดย่อย:

- **ข้อมูลการดูแล**: บันทึกบริบท แก้ไขเป็นฉบับใหม่ ตรวจยืนยัน และดูการเปรียบเทียบรายคน
- **งานดูแล**: แผนและงานตามกำหนดเดิม รับงาน บันทึกเสร็จ หรือข้ามพร้อมเหตุผล
- **สรุปประจำวัน**: เลือกวันที่ตามเวลาไทย ดูร่างและหลักฐาน ตรวจทาน และดาวน์โหลด Text

ไม่ต้องเพิ่ม dependency หรือเทรนโมเดลใหม่เพื่อเปิดสองฟีเจอร์นี้
ต้อง restart backend เพื่อสร้างตาราง/คอลัมน์เพิ่มเติม ไม่ต้องลบฐานข้อมูลเดิม
ถ้าเปิดผ่าน launcher ใช้ `python3 scripts/run_ward.py --restart` จากรากโปรเจ็กต์
ถ้ารันด้วย `next start` ต้อง build frontend ใหม่ก่อน; `next dev` จะโหลดการแก้ไขเอง

## 1. ข้อมูลการดูแลรายบุคคล

กรอกโรค/ภาวะที่ทราบ รายการยาที่มีบันทึก ประวัติแพ้ ข้อจำกัด หมายเหตุ และป้ายชื่อ
ผู้ดูแลได้ ช่องว่างหมายถึง **ยังไม่ได้บันทึก** ไม่ใช่ยืนยันว่าไม่มีโรคหรือไม่มีประวัติแพ้
ข้อมูลโรคในทะเบียนสังเคราะห์ถูกแสดงแยก และไม่ถูกเติมเป็นประวัติที่ยืนยันโดยอัตโนมัติ

1. กรอกข้อมูลและกด **บันทึกร่างโปรไฟล์** เพื่อสร้างเวอร์ชันใหม่
2. ตรวจข้อมูล เลือกช่องยืนยัน แล้วกด **ยืนยันโปรไฟล์ฉบับร่าง**
3. ฉบับที่ยืนยันแล้วจึงใช้เปรียบเทียบ ขณะมีร่างใหม่ ฉบับเดิมยังใช้ต่อ
4. **พักการเปรียบเทียบรายคน** จะหยุดใช้โปรไฟล์ แต่เก็บประวัติไว้
5. หากสองหน้าจอแก้ไขพร้อมกัน API ปฏิเสธเวอร์ชันเก่าด้วย 409 ให้โหลดล่าสุดก่อน

บัญชี `clinician` ยังเป็นบัญชีสาธิตร่วม การบันทึกชื่อบัญชีและเวลาจึงไม่ใช่การยืนยัน
ตัวแพทย์หรือระบบลงนามทางคลินิก ป้ายชื่อผู้ดูแลไม่ใช่บัญชีผู้รับ Push

### เปรียบเทียบสองแบบ โดยไม่แก้เกณฑ์แจ้งเตือนเดิม

- **ขอบเขตที่คนกรอก**: HR, SpO2, RR ใส่ต่ำ/สูงเป็นคู่หรือเว้นว่างทั้งคู่
  ไม่มีเกณฑ์โรคสำเร็จรูป และไม่ลดระดับ alert เดิมแม้ค่าวัดอยู่ในขอบเขตส่วนบุคคล
- **ช่วงอ้างอิงเชิงสถิติ**: เปิดได้เป็นตัวเลือก ใช้ snapshot ก่อนเวลายืนยัน
  คำนวณมัธยฐานและเปอร์เซ็นไทล์ 5–95 แล้วตรึงไว้ ไม่ใช่ online learning
  ไม่ใช่ช่วงความมั่นใจทางคลินิก และข้อมูลอ้างอิงอาจมีความผิดปกติอยู่แล้ว

เงื่อนไขซอฟต์แวร์สาธิตสำหรับช่วงอ้างอิง:

- เลือกย้อนหลัง 5–1,440 นาที ต้องมีอย่างน้อย 60 snapshot ที่ผ่านคุณภาพทั้งสามค่า
  และครอบคลุมระยะอย่างน้อย 295 วินาที
- ช่องว่างต้องไม่เกิน 15 วินาที และความครอบคลุมโดยประมาณต้องถึงอย่างน้อย 80%
  ของหน้าต่างที่เลือก โดยให้แต่ละ snapshot แทนเวลาได้ไม่เกิน 5 วินาทีและไม่นับช่วงซ้อนซ้ำ
- ไม่ผสม MQTT กับ BIDMC; replay ต้องเป็น recording/รอบเดียวกันและมี provenance
  ข้อมูลเก่าที่ไม่มี source segment จึงอาจใช้สร้างช่วงอ้างอิงไม่ได้
- ใช้เทียบเฉพาะค่าหลังยืนยัน ข้อมูลล่าสุดไม่เกิน 15 วินาที และแหล่ง/รอบต้องตรงกัน
- ช่วงอ้างอิงหมดอายุ 24 ชั่วโมง ต้องสร้างร่างใหม่และให้คนตรวจใหม่
  ระบบไม่ปรับค่าที่ตรึงไว้ตามสัญญาณใหม่อย่างเงียบ ๆ

หน้าเปรียบเทียบโหลดทุก 5 วินาทีและแสดงเหตุผลเมื่อไม่สามารถเปรียบเทียบได้
replay ที่วนรอบทุกความยาว recording หรือมีข้อมูลขาด อาจทำให้ต้องรอและทบทวนใหม่
นี่เป็นข้อจำกัดของสาธิต ไม่ใช่หลักฐานว่าตัวผู้ป่วยมีอาการเปลี่ยนแปลง

## 2. สรุปประจำวันจากหลักฐาน

Worker ทำงานใน backend บุคลากรประมาณทุก 5 นาที ไม่ต้องล็อกอินหรือเปิดหน้าเว็บไว้
งานสรุปรันใน thread แยกจาก event loop ที่รับและกระจายข้อมูลสด แต่ยังใช้ SQLite
ร่วมกัน จึงต้องทดสอบโหลดและวางแผน retention ก่อนใช้งานต่อเนื่องระยะยาว
ปิด backend แล้ว worker จะหยุด ไม่ใช่บริการรับประกัน 24 ชั่วโมง

รายงานใช้วัน `Asia/Bangkok` และช่วง `[00:00, เวลาตัดข้อมูล)`:

- สถิติ HR/SpO2/RR กราฟเฉลี่ยรายชั่วโมง และหมายเลขแถวหลักฐาน
- แยกสถิติตาม `BIDMC_REPLAY`, `MQTT` หรือ `UNKNOWN` ไม่เฉลี่ยรวมกัน
- ไม่นำค่า glucose/sleep/โรคในทะเบียนสมมติมาอ้างเป็นผลตรวจ
- ชั่วโมงที่ไม่มีข้อมูลเป็นช่องว่าง ไม่เติมศูนย์หรือค่าสังเคราะห์
- ประมาณความครอบคลุมจาก snapshot และแสดงช่วงข้อมูลหาย
  ความครอบคลุมนี้ไม่พิสูจน์ว่าอุปกรณ์หรือเครือข่ายออนไลน์จริงทุกวินาที
- ประวัติการประเมิน ML ที่ worker บันทึกจริง: รอบพร้อม รอบงดประเมิน
  และรอบที่พบรูปแบบต่างจากชุดฝึก ไม่ใช่จำนวนเหตุการณ์โรคหรือเปอร์เซ็นต์ความแม่นยำ
- alert ใหม่/ปิด/ยังค้าง ณ เวลาตัดข้อมูล งานดูแล และโปรไฟล์ที่ยืนยันแล้ว ณ เวลานั้น
  ไม่เอาข้อความงานที่บันทึกหลังเวลาตัดข้อมูลมาแสดงเป็นข้อมูลในอดีต

**ข้อความสรุปเป็น local template จากสถิติและผล ML ที่บันทึกไว้ ไม่ได้เรียก Gemini
และไม่ใช่โมเดลใหม่ที่เทรนเพิ่ม** โมเดลเดิมยังประเมินสัญญาณตาม pipeline เดิม
การระบุวิธีนี้ช่วยแยกส่วนที่เป็น ML ออกจากกฎ/สถิติอย่างตรวจสอบได้

### การตรวจทานและส่งต่อ

1. เลือกวัน แล้วดูเวลาสร้างร่างและเวลาตัดข้อมูล หากต้องการใหม่กด **สร้างร่างจากข้อมูลล่าสุด**
2. ตรวจหลักฐานและข้อจำกัด เลือกช่องยืนยัน แล้วใส่บันทึกผู้ตรวจทาน
3. กด **บันทึกฉบับที่ตรวจทานแล้ว** ระบบเก็บสำเนาแยกพร้อม SHA256 และชื่อบัญชี
4. ดาวน์โหลด Text ของร่างหรือฉบับที่ตรวจแล้วได้ มี structured evidence ประกอบ

ถ้า worker เปลี่ยนร่างระหว่างที่เปิดอ่าน ระบบปฏิเสธการตรวจ/ดาวน์โหลดร่างเก่าด้วย 409
ให้สร้างและอ่านฉบับล่าสุดก่อน สำเนาที่เคยตรวจแล้วไม่ถูกเขียนทับและยังดาวน์โหลดได้
ฉบับใหม่ไม่ได้รับสถานะตรวจแล้วตามฉบับเก่าโดยอัตโนมัติ

### ข้อจำกัดของประวัติ

- เก็บประวัติ ML ตั้งแต่ติดตั้งฟีเจอร์นี้ ไม่คำนวณย้อนหลังแล้วอ้างว่าเคยประเมิน/แจ้งเตือน
- Worker อัปเดตร่างวันนี้และปิดร่างของเมื่อวานหลังเปลี่ยนวัน วันที่เก่ากว่านั้นสร้างตามคำขอ
- การเพิ่มข้อมูลย้อนหลังอาจทำให้ร่างที่สร้างใหม่ต่างจากสำเนาเดิม สำเนาที่ตรวจแล้วยังคงเดิม
- รายการหลักฐานบางกลุ่มแสดงสูงสุด 100 รายการ แต่จำนวนรวมคำนวณครบ
- ยังไม่มี retention/archiving อัตโนมัติ SQLite จะโตตาม vitals และ ML history
  ต้องกำหนดนโยบายสำรองข้อมูล อายุข้อมูล และทดสอบโหลดก่อน deploy ระยะยาว
- Staff endpoint ในคู่มือนี้ยังไม่เปิดให้ patient portal; ฝั่งผู้ป่วยมี read-only projection
  ผ่าน `/api/me/care` และ `/api/me/daily` แยกต่างหาก โดยไม่ส่งบันทึกภายในหรือฉบับร่าง
  ดู [คู่มือฝั่งผู้ป่วย](PATIENT_PORTAL.md) ไม่มี Push ใหม่ ไม่มีการติดต่อคนจริง
  ไม่ส่งโปรไฟล์หรือรายงานนี้เข้า cloud และไม่เปลี่ยนเกณฑ์แจ้งเตือนสด

## ทดสอบ

จาก `backend/`:

```bash
PYTHONDONTWRITEBYTECODE=1 ../.venv/bin/python -m unittest discover -s tests -v
```

จาก `frontend/`:

```bash
npm run lint
npm test
npm run build
npm run build:patient
```

ใช้ฐานข้อมูลชั่วคราวแยกในการทดสอบ ไม่ใช้ข้อมูลหรือรหัสผ่านจริง
ครอบคลุมเวอร์ชัน การยืนยัน/พักโปรไฟล์ การงดเปรียบเทียบ การแยกแหล่งข้อมูล
ขอบเขตวันไทย การไม่ใช้ข้อมูลอนาคต สิทธิ์บุคลากร และสำเนารายงานที่ไม่ถูกเขียนทับ
