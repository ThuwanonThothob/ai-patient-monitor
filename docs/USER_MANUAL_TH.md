# คู่มือ Smart Ward — ภาษาไทย

ปรับปรุง 17 ตุลาคม 2569 · สำหรับผู้พัฒนา บุคลากร ผู้ป่วยและผู้ดูแลที่ร่วมทดสอบ

> ใช้ข้อมูล TEST/ข้อมูลวิจัยเท่านั้น ยังไม่ใช่เครื่องมือแพทย์ที่ผ่านการตรวจสอบทางคลินิก
> ไม่ใช้แทนการประเมินของบุคลากรหรือช่องทางฉุกเฉิน

## 1. โปรเจ็กต์นี้ทำอะไร

Smart Ward เป็นระบบต้นแบบติดตามผู้ป่วย มีเว็บบุคลากรและเว็บผู้ป่วยแยกกัน
รับข้อมูล → ตรวจคุณภาพ → ประเมินด้วยโมเดล → บันทึก → แสดงผล/สร้างรายการให้ตรวจสอบ
มีแผนดูแล แชท รายงาน และระบบแจ้งเตือนที่ต้องตั้งค่าก่อนส่งจริง

- ทะเบียนสาธิต 60 คน: A001–A020, B001–B020, C001–C020
- TEST_P เป็นผู้ป่วยทดสอบเพิ่มเติม แยกจากยอดเตียงสาธิต 60 คน
- ค่าหลักที่ใช้วิเคราะห์: HR ชีพจร, SpO₂ ออกซิเจนในเลือด, RR อัตราการหายใจ
- โรค กรุ๊ปเลือด น้ำตาล ไขมัน การนอน และข้อความ ECG ในโปรไฟล์สาธิต
  ไม่ใช่ค่าที่เซนเซอร์ตรวจวัดจริงหรือ label โรคจาก BIDMC
- งานเบื้องหลังทำงานเมื่อ backend เปิดอยู่ ไม่ต้องมีคนเปิดหน้าเว็บค้างไว้
  แต่รันบน Mac แล้วปิดเครื่อง/พักเครื่อง ไม่ได้แปลว่าจะทำงานต่อ 24 ชั่วโมง

### ติดตั้งเมื่อย้ายเครื่อง/ยังไม่มี dependencies

```bash
python3 -m venv .venv
source .venv/bin/activate
python3 -m pip install -r backend/requirements.txt
npm --prefix frontend ci
python3 scripts/run_ward.py --check
python3 scripts/run_ward.py
```

ต้องมี Python และ Node/npm ที่เข้ากันกับ dependencies ของโครงการ
Launcher เตรียม BIDMC/โมเดลเมื่อไม่มี จึงอาจใช้อินเทอร์เน็ตและเวลาในครั้งแรก
อย่านำไฟล์โมเดล joblib จากแหล่งที่ไม่เชื่อถือมาโหลด

### คำสั่งควบคุมระบบด้วย npm scripts (แนะนำ)

นอกจากคำสั่ง python3 โดยตรงแล้ว โครงการได้เพิ่ม npm scripts อำนวยความสะดวกใน `package.json` สามารถสั่งงานได้จาก root ของโปรเจ็กต์ทันที:

```bash
npm run ward:start    # เปิดระบบ Ward ทั้งหมด (ทั้ง Backend API และ Frontend สองฝั่ง)
npm run ward:status   # ตรวจสอบสถานะว่าระบบและบริการแต่ละพอร์ตเปิดอยู่หรือไม่
npm run ward:restart  # รีสตาร์ทระบบ Ward ทั้งหมด
npm run ward:stop     # สั่งหยุดการทำงานของระบบ Ward ทั้งหมดอย่างปลอดภัย
```

คำสั่งเหล่านี้จะรันสคริปต์ `./.venv/bin/python scripts/run_ward.py` โดยอัตโนมัติ

### หยุด/เปิดใหม่/ใช้ production build (Python Script)

```bash
python3 scripts/run_ward.py --stop
python3 scripts/run_ward.py --restart
```

ถ้าต้องการ production build ให้หยุดชุดเดิมก่อน แล้วทำตามลำดับนี้:

```bash
python3 scripts/run_ward.py --stop
npm --prefix frontend run build
npm --prefix frontend run build:patient
python3 scripts/run_ward.py --production
```

Production build ไม่ใช่การ Deploy และไม่ใช่การรับรองความพร้อมทางการแพทย์

## 3. ใช้งานฝั่งบุคลากร

1. เข้าสู่ระบบ แล้วดู **ภาพรวม**: จำนวนคนในสิทธิ์ ข้อมูลล่าสุด และคนที่ต้องตรวจสอบ
2. เข้า **ผู้ป่วย** ค้นหา ID/ชื่อ/โซน/ห้อง แล้วเปิดรายละเอียด
3. อ่านค่าล่าสุดและเวลาที่วัดก่อน อ่านกราฟย้อนหลังและแหล่งข้อมูลประกอบ
4. เลือกมุมมองพยาบาล/แพทย์เพื่อจัดลำดับข้อมูลที่ดู การสลับมุมมองนี้
   เป็นการจัดหน้าจอ ไม่ใช่การเปลี่ยนสิทธิ์บัญชี
5. เข้า **ลำดับการดูแล/รายการแจ้งเตือน** ตรวจหลักฐานก่อนรับทราบ ส่งต่อ หรือปิดงาน
6. ใน **แผนดูแล** ตรวจทานแผนก่อนใช้งาน บันทึกผลตามสิ่งที่ทำจริง
7. ใช้ **แชทระหว่างแพทย์และผู้ป่วย** ติดต่อบัญชีที่ดูแล แยกจากปุ่มลอยถาม Agentic ที่มุมล่างขวา
8. **AI และประวัติระบบ/พิสูจน์ AI** ใช้ดูขั้นตอน Agent ผลโมเดล และหลักฐานการทดลอง
9. **รายงาน** และรายละเอียดผู้ป่วยมี Text/Word ตามรายการที่รองรับ
   ตรวจทานข้อมูลและช่วงเวลาก่อนนำไปใช้หรือส่งต่อ

### ฟีเจอร์อำนวยความสะดวกสำหรับบุคลากร (Staff Productivity & Safety)

- **ปุ่มเสียงเตือนวิกฤต (Critical Alarm Chime):**
  - ปุ่มควบคุมอยู่ที่มุมขวาบนของ Header: `🔊 เสียงเตือนวิกฤต: เปิด` หรือ `🔇 เสียงเตือนวิกฤต: ปิด`
  - ใช้ Web Audio API สังเคราะห์เสียงเตือนอัตโนมัติ (ความถี่ 880 Hz สลับ 660 Hz) ทันทีที่มีเตียงใดเปลี่ยนสถานะเป็น `CRITICAL` เพื่อให้บุคลากรทราบเหตุการณ์เร่งด่วนทันทีแม้ไม่ได้มองหน้าจอตลอดเวลา
  - มีระบบป้องกันเสียงเตือนล้น (Rate limiting ไม่ดังซ้ำถี่เกินไปใน 8 วินาที) เพื่อลดความเหนื่อยล้าจากสัญญาณเตือน (Alarm Fatigue) และจำลองการตั้งค่าเปิด/ปิดไว้ใน localStorage
- **ตัวกรองด่วน (Quick Filters):**
  - ในหน้า **ภาพรวม (Overview)**: มีปุ่มตัวกรองด่วน `ทั้งหมด`, `เร่งด่วน (Critical)`, และ `เฝ้าระวัง (Warning)` ให้เลือกคัดกรองเฉพาะเตียงที่มีความผิดปกติได้ใน 1 คลิก
  - ในหน้า **ลำดับการดูแล (Triage)** และ **รายการที่ต้องติดตาม (Alerts)**: กรองตามโซน (A, B, C, HOME) หรือระดับความเร่งด่วนเพื่อจัดลำดับการตรวจเยี่ยมเตียงได้อย่างรวดเร็ว
- **คีย์ลัด `/` ค้นหาผู้ป่วยด่วน (Keyboard Shortcut `/`):**
  - ออกแบบตามหลักสรีรศาสตร์ของการทำงาน (Ergonomics): เมื่ออยู่หน้าจอใดก็ตาม เพียงกดปุ่ม `/` บนแป้นพิมพ์ (ขณะที่เคอร์เซอร์ไม่ได้อยู่ในกล่องกรอกข้อความ) ระบบจะสลับไปยังแท็บ "ผู้ป่วย" ทันที และโฟกัสเคอร์เซอร์ลงในช่องค้นหาโดยอัตโนมัติ
  - บุคลากรสามารถพิมพ์ค้นหารหัสผู้ป่วย เช่น `A001`, `B012`, `TEST_P` หรือพิมพ์ชื่อโรค/ห้อง แล้วกด Enter เพื่อเปิดดูข้อมูลได้ทันที
- **บันทึกด่วนและส่งต่อ (Quick Notes & Audit Trail):**
  - ในหน้ารายการแจ้งเตือน (Alerts Workflow) มีช่อง `ผลตรวจสอบ / เหตุผลส่งต่อ` สำหรับบันทึกสิ่งที่ตรวจพบและการดำเนินการ
  - รองรับ 3 ขั้นตอนการจัดการ: `รับผิดชอบงานนี้` (ACKNOWLEDGED), `บันทึกส่งต่อประเมิน` (ESCALATED), และ `บันทึกผลและปิดงาน` (RESOLVED)
  - ระบบบังคับให้พิมพ์บันทึกอย่างน้อย 5 ตัวอักษรก่อนกดส่งต่อหรือปิดงาน เพื่อให้มีบันทึก Audit Trail ชัดเจนเสมอว่าใครตรวจพบอะไรและจัดการอย่างไร ป้องกันการกดปิดงานโดยไม่มีเหตุผลกำกับ

ปุ่มคำขอติดต่อแพทย์/รถพยาบาลเป็นการบันทึกคำขอในระบบ
ไม่ได้โทรออกหรือเรียกรถพยาบาลจริง

## 4. ใช้งานฝั่งผู้ป่วย/ผู้ดูแล

- **ภาพรวม:** อ่านค่าล่าสุด เวลา และสถานะการเชื่อมต่อ
- **แนวโน้มย้อนหลัง:** เลือก 1 ชั่วโมง, 6 ชั่วโมง, 24 ชั่วโมง หรือ 7 วัน
  แล้วเลือกแหล่งข้อมูล อย่าเปรียบเทียบข้อมูลจำลองเหมือนเป็นค่าจากคนไข้จริง
- **แผนดูแลของฉัน:** ดูแผนที่บุคลากรตรวจทานแล้วและติดตามสถานะงาน
- **แชททีมดูแล:** ส่งข้อความถึงทีม ไม่ใช่แชทกับ AI และไม่ใช่ช่องทางฉุกเฉิน
- **สรุปประจำวัน:** เลือกวัน ตรวจเนื้อหา แล้วดาวน์โหลดสรุปที่ระบบเปิดให้ดู
- **ข้อมูลของฉัน:** ตรวจโปรไฟล์และบริบทการดูแล แยกข้อมูลสาธิตจากข้อมูลที่ยืนยัน

### ฟีเจอร์อำนวยความสะดวกสำหรับผู้ป่วยและผู้ดูแล (Accessibility & 1-Tap Care)

- **ปุ่ม `ก+ ตัวอักษรใหญ่` (Large Font Accessibility):**
  - ปุ่มอยู่บริเวณมุมบนขวาของหน้าจอ (`ก+ ตัวอักษรใหญ่` หรือ `ก+ ตัวอักษรใหญ่: เปิด`)
  - ออกแบบตามหลัก Universal Design สำหรับผู้สูงอายุหรือผู้ป่วยที่มีปัญหาทางสายตา ช่วยขยายขนาดตัวอักษร ตัวเลขสัญญาณชีพ และปุ่มกดให้ใหญ่ขึ้นอย่างเห็นได้ชัด เพิ่มระยะห่างระหว่างบรรทัดให้อ่านง่าย
  - ระบบจะจำสถานะการเปิดใช้งานไว้ในเบราว์เซอร์อัตโนมัติ ทำให้ไม่ต้องกดใหม่ทุกครั้งที่กลับเข้ามา
- **คำอธิบายค่าสัญญาณชีพเบื้องต้น (Layperson Vital Signs Guide):**
  - ในหน้าภาพรวม มีกล่องพับ `คำอธิบายค่าสัญญาณชีพเบื้องต้น (อ่านเข้าใจง่าย)` เพื่ออธิบายความหมายของตัวเลขสัญญาณชีพด้วยภาษาที่เข้าใจง่าย:
    - **อัตราการเต้นหัวใจ (bpm):** จำนวนครั้งที่หัวใจเต้นใน 1 นาที โดยค่าอาจสูงขึ้นชั่วคราวหลังขยับตัว เปลี่ยนท่าทาง หรือพูดคุย
    - **ออกซิเจนในเลือด (SpO₂ %):** สัดส่วนออกซิเจนที่จับกับเม็ดเลือดแดง หากตัวเลขแกว่งหรือขาดช่วงมักเกิดจากเซนเซอร์ที่นิ้วหลวม มือเย็น หรือการขยับนิ้ว
    - **อัตราการหายใจ (ครั้ง/นาที):** จำนวนครั้งที่หายใจเข้า-ออกใน 1 นาที ซึ่งอาจเปลี่ยนแปลงได้ตามปกติขณะพูดคุยหรือไอ
    - มีข้อความย้ำเตือน: ตัวเลขบนหน้าจอใช้ประกอบการติดตามของทีมดูแล ห้ามนำไปปรับยาหรือวินิจฉัยอาการด้วยตนเอง หากรู้สึกไม่สบายให้แจ้งบุคลากรโดยตรง
- **ปุ่มข้อความด่วน 1-Tap (1-Tap Quick Action Presets):**
  - ช่วยให้ผู้ป่วยหรือผู้ดูแลติดต่อทีมดูแลได้ใน 1 สัมผัส โดยไม่ต้องพิมพ์ข้อความยาว:
    - **ในแท็บแจ้งเรื่องให้ทีมดูแล (Care Messages):** มี 4 ปุ่มข้อความด่วนสำเร็จรูป:
      1) `ขอช่วยปรับท่าทางบนเตียง` (ขอความช่วยเหลือปรับท่าทางหรือพลิกตัวบนเตียงตามรอบการดูแล)
      2) `เซนเซอร์หลวม / สัญญาณขาด` (อุปกรณ์วัดสัญญาณชีพที่นิ้วหรือเตียงหลวม รบกวนช่วยตรวจสอบอุปกรณ์)
      3) `แจ้งอาการอ่อนเพลีย / ไม่สบายตัว` (รู้สึกอ่อนเพลียหรือไม่สบายตัวเล็กน้อย รบกวนทีมดูแลช่วยประเมินในรอบถัดไป)
      4) `สอบถามแผนดูแลวันนี้` (ต้องการสอบถามตารางเวลาและแผนการดูแลของวันนี้เพิ่มเติม)
    - **ในแท็บแชททีมดูแล (Care Chat):** มีปุ่มตอบรับด่วน เช่น `ได้รับข้อมูลแผนการดูแลแล้ว ขอบคุณครับ/ค่ะ`, `รบกวนสอบถามเวลาตรวจเยี่ยมรอบถัดไปครับ/ค่ะ`, และ `อุปกรณ์วัดสัญญาณชีพขึ้นรอข้อมูลใหม่ รบกวนช่วยดูให้หน่อยครับ/ค่ะ`

ระบบผูกข้อมูลกับ ID ในเซสชัน ไม่ใช้การพิมพ์ ID คนอื่นเพื่อสลับผู้ป่วย

## 5. อ่านกราฟอย่างไร

- HR หน่วย bpm, SpO₂ หน่วย %, RR หน่วยครั้ง/นาที
- ตัวเลขใหญ่คือ **ค่าล่าสุดที่มีในช่วงกราฟ** ไม่จำเป็นต้องเป็นค่าปัจจุบัน
- แต่ละกราฟมีสเกลแยกกัน อย่าเทียบความสูงของเส้นต่างตัวแปรโดยตรง
- กราฟย้อนหลังเป็นค่าเฉลี่ยตามช่วงเวลา ไม่ใช่ค่าทุกวินาที
- ชี้กราฟเพื่อดูวันเวลาไทยและค่า หรือกด **ดูตาราง** เพื่ออ่านตัวเลข
- ช่องว่าง/ไม่มีข้อมูลไม่เท่ากับค่าศูนย์ ไม่ได้ยืนยันว่าผู้ป่วยปลอดภัย
- หากข้อมูลเก่า ระบบระงับการใช้ผลบางส่วน รอข้อมูลใหม่หรือตรวจอุปกรณ์

## 6. ถาม Agentic และแยกจาก AI ส่วนอื่น

กดปุ่มลอย **ถาม Agentic** ที่มุมล่างขวาของหน้าจอเพียงจุดเดียว (หน้าต่างจะเปิดขึ้นมาตรงกลางหน้าจอ)
ฝั่งบุคลากรเลือกผู้ป่วยก่อน หรือใส่ ID ในผู้ช่วย ส่วนผู้ป่วยใช้ ID จากเซสชัน

ตัวอย่างคำถาม:

- สรุปค่าล่าสุด
- อ่านกราฟแนวโน้มย้อนหลัง
- มีงานดูแลอะไรบ้าง
- สรุปค่าล่าสุด แนวโน้ม และงานดูแล

ระบบตรวจสิทธิ์ อ่านค่าล่าสุด ตรวจผลโมเดลเดิม แล้วเลือกอ่านสถิติ/งานดูแล
ตามกฎและคำสำคัญ กด **ดูเครื่องมือและขั้นตอน** เพื่อตรวจสิ่งที่ทำจริง
ผู้ช่วยอ่านแนวโน้มย้อนหลัง **24 ชั่วโมง** แม้กราฟที่เลือกจะเป็นช่วงอื่น
คำตอบไม่อัปเดตเอง ต้องกดถามใหม่เพื่ออ่านข้อมูลล่าสุด

| ส่วน | หน้าที่จริง | ไม่ควรอ้างว่า |
| --- | --- | --- |
| โมเดล ML | คาดการณ์ HR/RR และตรวจรูปแบบต่างจากชุดฝึก | วินิจฉัยได้ทุกโรค |
| Agent เบื้องหลัง | ตรวจข้อมูลและสร้างงานทบทวนตาม policy พร้อม trace | แพทย์/พยาบาลอัตโนมัติเต็มรูปแบบ |
| ปุ่มถาม Agentic | เลือกเครื่องมืออ่านข้อมูลแบบ deterministic | LLM ที่วางแผนอิสระหรือเรียนรู้เอง |
| Gemini เพิ่มเติม | ช่วยอธิบาย/ตอบคำถามเมื่อ API พร้อม | แหล่งข้อเท็จจริงที่รับรองความถูกต้องทุกคำตอบ |

Agentic ใหม่ไม่เรียก Gemini ไม่ส่งข้อมูลให้ cloud LLM ไม่แก้แผนหรือสั่งยา
Gemini เดิมเป็นอีกส่วนหนึ่ง อาจใช้ quota/มีค่าใช้จ่ายตามบัญชีที่ตั้งไว้

## 7. Dataset และผลโมเดล

โมเดล monitoring หลักพัฒนาจาก **PhysioNet BIDMC PPG and Respiration Dataset v1.0.0 (Sampling Rate 1 Hz)**
โครงการนำข้อมูลตัวเลขสัญญาณชีพจริง HR / SpO₂ / RESP มาประมวลผล (ไม่ได้ใช้คลื่นดิบ ECG/PPG มาเทรน)

- **การแบ่งกลุ่ม Train / Validation / Test (Zero Data Leakage):**
  - ข้อมูลถูกจัดกลุ่มอย่างเคร่งครัดตามรหัสไฟล์ผู้ป่วย โดยแยกไฟล์ในชุดฝึก (Train), ชุดปรับแต่ง (Validation) และชุดทดสอบ (Held-out Test) ออกจากกันอย่างเด็ดขาด
  - ไม่มีข้อมูลจากผู้ป่วยเดียวกันปะปนข้ามกลุ่ม ทำให้ผลการทดสอบสะท้อนความสามารถในการทั่วไปของโมเดล (Generalization) บนข้อมูลที่ไม่เคยเห็นจริง
- **การพยากรณ์ล่วงหน้า 30 วินาที (30s Lookahead Forecast):**
  - ใช้ข้อมูลสัญญาณชีพต่อเนื่องย้อนหลัง 60 วินาที (-59s ถึง 0s) มาสกัด Features ทางสถิติ
  - **Random Forest:** ใช้พยากรณ์ค่า HR และ RR ล่วงหน้า 30 วินาที (+30s)
  - **Persistence Baseline:** ใช้ค่าล่าสุดคงเดิมเพื่อเป็น baseline เปรียบเทียบมาตรฐาน (สำหรับ SpO₂ ที่มีความผันผวนชั่วคราวต่ำ Persistence Baseline ให้ค่าความคลาดเคลื่อน MAE ที่ต่ำมาก)
- **หลักการงดทาย (Abstain) เมื่อข้อมูลขาดช่วง (Clinical Safety First):**
  - หากเซนเซอร์หลุด สัญญาณรบกวน มีค่าผิดปกติ หรือข้อมูลขาดช่วงไม่ครบ 60 วินาที ระบบจะ **งดทาย (Abstain)** ทันที
  - ระบบไม่เดาค่า (No Hallucination) ไม่แปลงค่าที่ขาดหายเป็นศูนย์ และไม่คาดการณ์บนข้อมูลที่ไม่น่าเชื่อถือ เพื่อป้องกันการเกิดสัญญาณเตือนลวง (False Alarm) และไม่บดบังภาวะวิกฤตจริง
- **ข้อจำกัดสำคัญ:**
  - IsolationForest ตรวจจับรูปแบบที่ต่างจากชุดฝึกเพื่อส่งต่อให้คนทบทวน ไม่ได้มี label วินิจฉัยโรค
  - 60 เตียงเป็นการจำลองเล่นซ้ำจาก recording ไม่ใช่ผู้ป่วยอิสระ 60 คนในโรงพยาบาลจริง
  - Random Forest ยังไม่ชนะ persistence baseline ในทุกตัวแปร และผลการทดสอบบนข้อมูล ICU ยังไม่ใช่หลักฐานรับรองความแม่นยำกับผู้สูงอายุติดเตียงที่บ้าน

รายละเอียดการแบ่งชุดข้อมูล ผลวัด และงานวิจัยแยกอยู่ใน
[Dataset/Models](AI_DATASETS_AND_MODELS.md), [Agent](NURSE_AGENT.md),
[Research Lab](SEPSIS_RESEARCH_LAB.md)

## 9. แจ้งเตือนบนมือถือและ Cloud

ดู [Web Push](WEB_PUSH.md) และ [Cloud TEST](CLOUD_TEST.md) ก่อนตั้งค่าจริง
โค้ดมีการแจ้งเตือนรายการดูแลสำหรับบุคลากร รวมถึงแชท/TEST สำหรับผู้รับที่มีสิทธิ์
เอกสาร Web Push บางช่วงอธิบายเฉพาะรุ่นบุคลากรเดิม

ต้องมี VAPID key, dependencies, HTTPS ที่มือถือเข้าถึงได้ และอนุญาตจากอุปกรณ์
บน iPhone ใช้ขั้นตอนติดตั้งจากเว็บลงหน้าจอโฮมตามหน้าตั้งค่าระบบ
`localhost` บนโทรศัพท์ไม่ได้ชี้กลับมาที่ Mac

**ข้อจำกัดสำคัญ:** เซสชันปัจจุบัน 8 ชั่วโมง และ push ผูกกับเซสชัน
จึงยังห้ามอ้างว่ามือถือจะรับแจ้งเตือนต่อเนื่อง 24 ชั่วโมงโดยไม่ต้องเข้าใช้งานใหม่
Provider accepted ไม่เท่ากับมือถือได้รับหรือมนุษย์รับทราบ
Cloud package ยังต้องทดสอบ Docker/HTTPS/มือถือและการกู้คืนบน host จริง
ไม่มีการรับประกัน hosting ฟรีหรือ uptime 24/7 จากโค้ดชุดนี้
