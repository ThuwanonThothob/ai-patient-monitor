# Web Push และ Interface รุ่นใหม่

## สิ่งที่มีแล้ว

- หน้าบุคลากรและผู้ป่วยใช้ธีมเดียวกัน อ่านง่ายบน desktop / tablet / mobile
- แถบหมวดการทำงานภาษาไทย: ภาพรวม ลำดับการดูแล ผู้ป่วย รายการแจ้งเตือน
  แจ้งเตือนมือถือ AI/ประวัติระบบ Research Lab และรายงาน
- ภาพรวมแสดง **จำนวนเตียงที่มีค่าล่าสุด** ไม่ใช้จำนวนการวัดผิดปกติสะสมแทนจำนวนคน
- ตารางรายงานยังเป็นสถิติสะสม โดยมีคำอธิบายกำกับ
- ทะเบียนแบ่งหน้าครบ 60 คน ค้นหา ID/ชื่อ/ห้อง/โรค และกรองโซน
- รายละเอียดผู้ป่วยแยกข้อมูล/AI, แชท และประวัติ/ส่งต่อ มีปุ่มปิดและ Escape
- WebSocket ลองเชื่อมต่อใหม่พร้อมหน่วงเวลา มีการดึงข้อมูลสำรองทุก 5 วินาที
- ซ่อนค่าปัจจุบันเกิน 15 วินาที และระงับผลคาดการณ์เก่า ไม่แปลข้อมูลขาดว่า “ปกติ”
- สถานะโหลดผิดพลาดแยกจากผลค้นหาว่างหรืองานค้างเป็นศูนย์
- **หน้าบุคลากร (P2):** มีปุ่มเปิด/ปิดเสียงเตือนวิกฤต (`🔊 เสียงเตือนวิกฤต`, Web Audio API), ตัวกรองด่วนในหน้าภาพรวม (`ทั้งหมด` / `เร่งด่วน` / `เฝ้าระวัง`) และปุ่มลัด `/` เพื่อค้นหาผู้ป่วยทันที
- **หน้าผู้ป่วย (P3):** มีปุ่มขยายขนาดตัวอักษร (`ก+ ตัวอักษรใหญ่`) สำหรับผู้สูงอายุ/ผู้ป่วยติดเตียง, คำอธิบายค่าสัญญาณชีพภาษาเข้าใจง่าย และปุ่มข้อความด่วน (1-Tap Quick Care Chips) ในหน้าแจ้งเรื่องและหน้าแชท

Web Push เป็น **ช่องทางเสริมสำหรับทั้งบุคลากรและผู้ป่วย** (รองรับการแจ้งเตือนงานติดตามของบุคลากร, ข้อความแชทระหว่างทีมดูแลกับผู้ป่วย และการแจ้งเตือนจำลอง `TEST`) ไม่ใช่ระบบฉุกเฉินหลัก และไม่ได้
ทำให้โมเดลวิจัยกลายเป็นเครื่องมือแพทย์ที่ผ่านการรับรอง ไม่ใช้กับผู้ป่วยจริงก่อน
ทดสอบทางคลินิก ทบทวนความเป็นส่วนตัว และจัดระบบสำรองที่เหมาะสม

## สถานะเริ่มต้น

ปิดการส่งจริง (`WARD_WEB_PUSH_ENABLED=0`) ไม่มีการสร้าง key หรือสมัครอุปกรณ์ให้เอง
แพ็กเกจอยู่ใน `backend/requirements-push.txt` แยกจากชุดเฝ้าระวังเดิม
หากไม่มีแพ็กเกจหรือ key ระบบเฝ้าระวังยังทำงานได้ และหน้าตั้งค่าจะแจ้งสิ่งที่ขาด

## 1. เตรียม backend

รันจาก root ของโปรเจ็กต์:

```bash
source .venv/bin/activate
python3 -m pip install -r backend/requirements-push.txt
python3 scripts/generate_push_keys.py
```

สคริปต์สร้าง `backend/runtime/webpush-private.pem` สิทธิ์อ่าน/เขียนเฉพาะเจ้าของ
และปฏิเสธการเขียนทับ key เดิม อย่าแชร์ key หรือ commit ไฟล์นี้
ไม่ใช่ Gemini API key และไม่ต้องใช้ Firebase API key

เพิ่มค่าลง `backend/.env` โดยใช้ path และอีเมลติดต่อของผู้ดูแลจริง:

```dotenv
WARD_WEB_PUSH_ENABLED=1
WARD_VAPID_PRIVATE_KEY_FILE=/Users/thuwanon/ai-patient-monitor/backend/runtime/webpush-private.pem
WARD_VAPID_SUBJECT=mailto:replace-with-your-real-email@example.org
```

อย่าใช้ค่าอีเมลตัวอย่างโดยไม่เปลี่ยน อย่าสร้าง key ใหม่ทุกครั้งที่รัน เพราะอุปกรณ์
ที่สมัครไว้ผูกกับ public key เดิม หากจำเป็นต้องหมุน key ให้หยุดการส่งและสมัครใหม่
บนอุปกรณ์ที่เกี่ยวข้อง

## 2. เตรียม HTTPS ที่โทรศัพท์เข้าถึงได้

`http://localhost:3000` บนโทรศัพท์หมายถึงตัวโทรศัพท์ ไม่ใช่คอมพิวเตอร์ที่รันระบบ
การเปิดผ่าน `http://192.168...` อย่างเดียวก็ยังไม่ใช่ secure context สำหรับ Web Push
ดูข้อกำหนด [Push API ของ MDN](https://developer.mozilla.org/en-US/docs/Web/API/Push_API)

ให้ผู้ดูแลเลือก hostname และ HTTPS reverse proxy ที่ไว้ใจได้ โดย:

1. ใช้ certificate ที่เบราว์เซอร์เชื่อถือ **ไม่ข้ามคำเตือน certificate**
2. staff hostname ส่งต่อไป `127.0.0.1:3000` และรองรับ WebSocket Upgrade
3. หากเปิด patient portal ด้วย ให้ใช้ hostname อีกชื่อส่งต่อไป `127.0.0.1:3001`
4. proxy ทุก path รวม `/api`, `/ws`, `/sw.js`, `/manifest.webmanifest` และไอคอน
   ไม่ cache `/api`, หน้า HTML ที่มี session หรือ `/sw.js`
5. เก็บ FastAPI 8000/8001 ไว้ loopback ไม่เปิดสู่เครือข่ายโดยตรง
6. ใช้การเข้าถึงแบบเครือข่ายทดสอบที่จำกัดคน อย่าเปิด ID-only patient login
   สู่ข้อมูลผู้ป่วยจริง หรือเปิดเผยระบบต่ออินเทอร์เน็ตโดยไม่มีการทบทวนสิทธิ์

ตั้ง origin แบบตรงตัว ไม่มี wildcard หรือ path:

```dotenv
WARD_STAFF_ORIGIN=https://staff.your-domain.example
WARD_PATIENT_ORIGIN=https://patient.your-domain.example
WARD_COOKIE_SECURE=1
```

เปลี่ยนเป็น hostname จริงของ proxy; ถ้าเปิดเฉพาะ staff ไม่ต้องตั้ง patient origin
เมื่อใช้ Secure cookie ให้เข้าผ่าน HTTPS hostname นั้น ไม่ใช่สลับกลับไป HTTP
origin ใหม่นี้ตรวจทั้ง HTTP และ WebSocket และไม่ใช้ Host header จาก client
เป็นเหตุให้ยอมรับ origin โดยอัตโนมัติ

การตั้งค่าข้างต้น **ไม่ได้สร้าง DNS, certificate หรือเปิด proxy ให้เอง**
ต้องมีช่องทาง HTTPS ที่ใช้งานได้ก่อน รวมถึง backend ต้องเปิดและต่ออินเทอร์เน็ต
เพื่อส่งคำขอไปบริการ Push ของเบราว์เซอร์

รีสตาร์ต stack ที่รันด้วย launcher:

```bash
python3 scripts/run_ward.py --restart
```

ถ้ารันแยก terminal ให้ restart backend ทั้งสองตัวและเปิด frontend ตามเดิม
อย่ารันหลาย Uvicorn workers เพราะจะซ้ำทั้งตัวเล่นข้อมูลและ dispatcher

## 3. สมัครโทรศัพท์และทดสอบด้วยตัวเอง

1. เปิด HTTPS URL ของ **หน้าบุคลากร** และเข้าสู่ระบบ
2. iPhone / iPad ที่รองรับ: Share → Add to Home Screen → เปิดจากไอคอนนั้น
   Web Push สำหรับ Home Screen web app รองรับตั้งแต่ iOS/iPadOS 16.4
   ตาม [เอกสาร WebKit](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/)
3. Android: ใช้เบราว์เซอร์ที่รองรับ Push API; ติดตั้งผ่านเมนูเบราว์เซอร์ได้
4. เปิดหมวด **แจ้งเตือนมือถือ** ตรวจว่าเซิร์ฟเวอร์พร้อม เลือกโซนและระดับ
5. กด **เปิดแจ้งเตือนเครื่องนี้** และให้เจ้าของโทรศัพท์กด Allow ด้วยตัวเอง
6. กด **ส่งข้อความทดสอบ** ตรวจประวัติการส่ง แล้วตรวจข้อความบนโทรศัพท์จริง
7. แตะข้อความ: ต้องกลับมาหน้าแจ้งเตือนใน origin เดิม และเข้าสู่ระบบก่อนดูข้อมูล
8. ทดสอบขณะปิดหน้าเว็บ/ล็อกจอ, เปิดโหมดห้ามรบกวน, เน็ตหลุด และ session หมดอายุ

การตั้งค่าเก็บแยกตามอุปกรณ์และ **session ปัจจุบัน** (อายุเริ่มต้น 8 ชั่วโมง พร้อม **Sliding Session Renewal** ต่ออายุอัตโนมัติเมื่อมีการใช้งานต่อเนื่องและเวลาเหลือน้อยกว่ากึ่งหนึ่ง)
ออกจากระบบ, ปิดใช้งานบัญชี (`--disable`), ลบบัญชี (`--delete`) หรือปล่อยให้ session หมดอายุจะหยุดส่งและยกเลิกคิวค้างทันที ต้องเข้าสู่ระบบและผูกอุปกรณ์อีกครั้ง
ปุ่มหยุดแจ้งเตือนหยุดเครื่องนี้ ไม่หยุดมือถือคนอื่น ข้อความที่ส่งไปแล้วอาจยังปรากฏได้
รองรับทั้งบัญชีรายบุคคลในฐานข้อมูล (`portal_accounts`) และบัญชีสาธิต (`WARD_DEMO_ID_LOGIN`) โดยเซสชันที่เข้าด้วยรหัสผ่านบัญชีจริงจะผูกกับสถานะของแถวบัญชีนั้นเสมอ (หากลบบัญชีทิ้ง เซสชันจะถูกเพิกถอนทันทีแม้ยังเปิดโหมดสาธิตอยู่)

## การส่งและข้อจำกัด

- Alert ใหม่ถูกบันทึกพร้อมคิว SQLite ใน transaction เดียว ไม่ส่งผ่าน HTTP/WebSocket handler
- Dispatcher ส่งใน worker thread พร้อม timeout 10 วินาที ไม่บล็อกการส่งสัญญาณชีพ
- ค่าเริ่มต้นรับเฉพาะ critical; เลือกรวม warning หรือจำกัด A/B/C ได้
- ไม่ดึง alert เก่ามาย้อนส่งเมื่อเพิ่งสมัคร และไม่ส่งรายการที่รับทราบ/ปิดแล้ว
- รวมรายการและจำกัดการส่งสำเร็จไม่เกินหนึ่งครั้งต่อนาทีต่ออุปกรณ์
- คิวหมดอายุเมื่อเกิน 5 นาที; provider TTL 60 วินาที
- Retry แบบหน่วงเวลาเมื่อ network/429/5xx สูงสุด 3 attempts
- HTTP 404/410 ปิด subscription ที่ใช้ไม่ได้ ต้องเปิดใหม่บนอุปกรณ์
- Retry หลัง timeout/crash อาจเกิดข้อความซ้ำ ใช้ notification tag ลดข้อความซ้อน
  **ไม่รับประกัน exactly-once, ส่งถึงเครื่อง, เสียงดัง หรือมีคนเห็น**
- หน้าจอล็อกไม่มีชื่อ ID โรค หรือ vital values; Service Worker ไม่ cache เวชระเบียน
- ตรวจ HTTPS endpoint ของ Apple/Google/Mozilla เท่านั้น และไม่ตาม HTTP redirect
  browser/provider อื่นอาจยังไม่รองรับ รายการ allowlist ไม่ได้ครอบคลุมทุกเบราว์เซอร์
- URL subscriptions และ encryption material เก็บใน SQLite; ต้องจำกัดสิทธิ์ไฟล์
  มีนโยบาย backup/retention และแยก secrets ในระบบที่จะใช้จริง

| สถานะ | ความหมาย |
| --- | --- |
| QUEUED / RETRY | รอส่ง / รอลองใหม่ |
| SENDING | เริ่มคำขอไปยังผู้ให้บริการ |
| ACCEPTED | ผู้ให้บริการตอบรับ ไม่ใช่หลักฐานว่าถึงเครื่องหรือมีคนรับทราบ |
| BUNDLED | รวมอยู่ในข้อความทั่วไปของอุปกรณ์ ไม่ได้ส่งแยกอีกครั้ง |
| FAILED | ส่งไม่สำเร็จ ให้ตรวจ error code และตั้งค่า |
| CANCELLED | ไม่มีสิทธิ์รับแล้ว หรือรายการไม่ต้องส่งแล้ว |
| EXPIRED | เก่าเกินกำหนด ไม่ส่งคำเตือนล้าสมัย |

สถานะงานทางคลินิก `NEW → ACKNOWLEDGED → ESCALATED → RESOLVED` เป็นคนละชุด
กับสถานะการส่ง Push การตอบรับจาก provider ไม่เปลี่ยนงานเป็น “รับทราบ” ให้เอง

## ตรวจสอบก่อนส่งมอบ

```bash
cd backend
PYTHONDONTWRITEBYTECODE=1 ../.venv/bin/python -m unittest discover -s tests -v
cd ../frontend
npm test
npm run lint
npm run build
npm run build:patient
```

Tests ใช้ฐานข้อมูลชั่วคราว/ปลายทาง HTTP จำลอง ครอบคลุม session isolation,
zone/severity, deduplication, retry, expiry, logout, endpoint allowlist, การเข้ารหัส
ด้วย pywebpush, ข้อความบน lock screen และ freshness การแสดงผล
การผ่าน tests และ build **ไม่แทนการทดสอบส่งถึงโทรศัพท์จริง**

อ้างอิงไลบรารี: [pywebpush](https://github.com/web-push-libs/pywebpush)
